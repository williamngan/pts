## Findings

### 1. P2: merging opaque SVG fills changes antialiased edges

Introduced by `f6632ea`. Location: [SVGContext2D._joinable](../src/Svg.ts#L966).

The merge rule allows overlapping opaque fills with compatible winding to share
a path. Opaque paint still has partially covered edge pixels. Painting an edge
twice composites those pixels twice; combining both shapes into one path paints
them once.

Reproduction with a 100 × 100 SVG and its `SVGContext2D`:

```js
const ctx = new Pts.SVGContext2D(svg);
const form = new Pts.CanvasForm(ctx);
ctx.beginFrame();
form
  .fillOnly("#000")
  .point([50.25, 50.25], 30, "circle")
  .point([50.25, 50.25], 30, "circle");
ctx.commitFrame();
```

Rasterizing the SVG onto a white canvas in Chromium gives two paths before the
reviewed commits and one afterward. **214 pixels change**, with a maximum channel
difference of **64**. At `(47, 20)`, the pixel changes from `[59, 59, 59, 255]` to
`[123, 123, 123, 255]`.

Both images use the same SVG rasterizer, so this comparison does not depend on
differences between Canvas and SVG antialiasing. Existing tests that sample the
interior of opaque shapes miss it.

Recommendation: retain separate paths for overlapping fills when exact rendering
is promised. Add a pixel comparison covering coincident curved edges. If this
optimization is retained, describe the rendering difference explicitly rather
than calling the merge exact.

### 2. P2: SVG `unset` paint is incorrectly classified as opaque

Introduced by `f6632ea`. Location: [_parseOpaque](../src/Svg.ts#L163).

The alphabetic named-color check excludes several special values but accepts
`unset`. For SVG fill, that value can inherit translucent paint from the parent.
The resulting shapes are merged as if their paint were opaque, reintroducing
the original overlap-compositing defect.

Reproduction, using the same setup as finding 1:

```js
svg.setAttribute("fill", "rgba(0,0,0,0.5)");
ctx.beginFrame();
form
  .fillOnly("unset")
  .rect([
    [10, 10],
    [60, 60],
  ])
  .rect([
    [40, 40],
    [90, 90],
  ]);
ctx.commitFrame();
```

The path count changes from two to one. **400 pixels change**; the overlap at
`(40, 40)` changes from grey **63** to **127** on white.

Recommendation: treat CSS inheritance and cascade keywords conservatively when
determining opacity. Add a native SVG regression test with translucent inherited
paint.

### 3. P2: lost-press recovery misses manually forwarded UI events

Incomplete fix in `1c99f9b`. Location:
[MultiTouchSpace._abandonPress](../src/Space.ts#L822).

Recovery cleans up UI objects registered through `space.track()`. It does not
reach objects using the supported manual forwarding pattern:

```js
space.add({
  action: (type, x, y, evt) =>
    Pts.UI.track([dragger], type, new Pts.Pt(x, y), evt),
});
```

Reproduction: create a `UIDragger` covering the input area, bind mouse input and
start playback, then dispatch this sequence on the canvas:

1. Mouse pointer 7: `pointerdown` at `(30, 30)`, then `pointermove` to `(40, 30)`.
2. Call `space.bindMouse(false).bindMouse()` without releasing pointer 7.
3. Mouse pointer 8: `pointerdown` at `(40, 30)`, `pointermove` to `(50, 30)`, then
   `pointerup` there.

With `space.track(dragger)`, the probe produces two drag callbacks, two drop
callbacks, and `dragging === false`. With manual forwarding, it produces one drag,
zero drops, and **`dragging === true`** after the sequence. The dragger retains
ownership of the abandoned pointer and refuses the new one.

A separate synthetic probe dispatching pen `pointerdown`, `lostpointercapture`,
then mouse down/move/up also produces no drag or drop for the new mouse sequence.
This identifies a recovery coverage gap; it is not a physical-device reproduction.

Recommendation: make cancellation/recovery observable through the manual action
path as well as automatic tracking, and test capture loss followed by a different
pointer type.

### 4. P2: Path sweep performance still depends heavily on input order

Tradeoff introduced by `47f5c83`. Location:
[Path sweep searchTree](../src/_path.ts#L550).

The new search restores performance for tall, jittered bars, but its blocks group
edges in x order. Shuffling disjoint full-width bars with equal x extents gives
those blocks broad y bounds. The heuristic then disables ineffective pruning,
leaving a quadratic candidate scan.

For the repository's 2,000-bar benchmark, the median changes from **6.05 ms before
these commits to 74.85 ms afterward**, about **12.4× slower**. The same bars in
their ordered arrangement take **4.88 ms** at the current head. The shuffled case
is approximately back to 1.0.2 performance rather than preserving the original
fix's improvement.

This tradeoff is acknowledged in the earlier review and has a benchmark. It
still means original audit item 10 is only partially fixed. `bench:check` is a
benchmark dry run, not a performance threshold check.

Recommendation: preserve effective y pruning when x extents tie, while keeping
the fast x cutoff for the transposed layout. Validate ordered, shuffled, tall,
and disjoint cases together, with the existing fuzz harness as the correctness
oracle.

### 5. P2: paused canvases still become blank on resize

Additional pre-existing gap, not a regression introduced by the reviewed commits.
Location: [CanvasSpace.resize](../src/Canvas.ts#L287).

The repaint condition checks `!this.isPlaying`. Calling `pause()` leaves
`isPlaying` true, so a ResizeObserver resize clears the backing canvas without
redrawing it.

Native Chromium reproduction: create a 100 × 100 space with automatic resize,
draw a red rectangle during animation, pause after a frame, and widen the host to
150 pixels. Pixel `(5, 5)` changes from `[255, 0, 0, 255]` to `[0, 0, 0, 0]`, while
`isPlaying` remains true. The canvas stays blank until playback resumes.

The stopped-space behavior addressed by `14fb7a8` works in the tested cases;
paused playback needs its own handling.

Recommendation: include paused spaces in resize redraw logic without resuming
animation. Add a native ResizeObserver test for the paused state.

### 6. P3: Pt lost its class documentation

Introduced by `cba0aa4`. Location: [Pt class JSDoc](../src/Pt.ts#L14).

The `_isBuffer` helper was inserted between the Pt class comment and the class
declaration. The generated Pt documentation now uses the inherited IPt interface
description and loses the Pt introduction and guide link.

Before, `docs/json/class/Pt_Pt.json` described Pt as a subclass of `Float32Array`
and linked the Pt guide. Afterward, its description begins “Typescript interface:
IPt is an interface …”. Artifact freshness checks pass because this incorrect
documentation is generated consistently.

Recommendation: place the class JSDoc immediately above `export class Pt`, then
regenerate the documentation.

### 2. `unset` paint

`inherit`, `initial`, `unset` and `revert` now count as translucent, and so do
names the browser does not accept as colors (`CSS.supports`), since an SVG
element given one takes its parent's paint. Unit tests cover the keywords. A
native test draws overlapping rectangles in `unset` and in an unknown name
under a half-transparent parent fill, and finds two elements and an overlap
alpha of 191 (one layer: 128).

### 3. Lost press

An abandoned press now reaches the players as a cancelled pointer does: `out`,
then `drop` if it dragged, at the last pointer position. UIs forwarded by
hand and tracked UIs recover alike, and so does a player's own drag state.
Players see these actions only while the space plays. A pointer press that has
lost its pointer capture may never see its release, so a first contact of any
kind now replaces it; one that holds its capture still cannot be taken by a
palm.

The browser suite runs the assessment's sequence through a manually forwarding
player and checks capture loss with stubbed capture, since synthetic events
cannot hold capture. For the same reason the assessment's synthetic pen probe
(`pointerdown`, `lostpointercapture`, mouse) still sees no takeover: the space
asks whether the pen holds capture, and a synthetic pen never did. With real
CDP input in Chromium, a pen press whose release is lost (the canvas leaves
the page mid-press and the pen lifts outside) left the dragger stuck before
the fix (1 drag, 0 drops, `dragging` true). After it, a mouse drag works (4
drags, 2 drops).

Behavior change: unbinding input mid-press now sends players `out`, and
`drop` if the press dragged. In react-pts-canvas this reaches `onAction` when
`input` changes during a press.

### A. P2: stopped-space input unbinding strands tracked draggers

Regression in `7331dbc`, at
[MultiTouchSpace._abandonPress](../src/Space.ts#L841).

The method clears the space's press state, then returns immediately when
`isPlaying` is false. This prevents both the new player notifications and the UI
cleanup that the preceding implementation performed even while stopped. The UI
retains the old contact identifier, but the space has forgotten that the contact
needs cancellation. A subsequent contact cannot recover that UI.

Reproduction using `space.track(dragger)` and `bindMouse()`:

1. Start playback, press with a touch pointer, and move to begin a drag.
2. Call `space.stop()` and wait until `space.isPlaying` is false.
3. Unbind mouse input, release the contact while unbound, then bind it again.
4. Call `space.replay()` and perform a new touch drag.

The native Chromium probe uses CDP touch input, which creates real browser pointer
events and capture state, rather than dispatched synthetic PointerEvents. The
first contact has pointer ID 2; the next has ID 3.

| Build     | Drag callbacks | Drop callbacks | Final `dragging` |
| --------- | -------------- | -------------- | ---------------- |
| `b6fc415` | 2              | 2              | `false`          |
| `9b461c6` | 1              | 0              | `true`           |

The space emits actions for the new contact, but the dragger ignores them because
it still belongs to the old contact. Synthetic probes independently reproduce
the regression. Manual forwarding also remains broken in the stopped-space case,
although that variant was already broken before this fix pass.

Recommendation: retain or defer the cancellation when playback is stopped, and
deliver cleanup before accepting the next contact. Preserve the intended policy
for player callbacks while stopped, while ensuring UI ownership is released.
Test both automatic tracking and manual forwarding across stop, unbind, rebind,
and replay.

### B. P2: cached `currentColor` stops following CSS color changes across frames

Regression exposed by `58ae9b9`, which removed cache invalidation in
[CanvasSpace._endDraw](../src/Canvas.ts#L493). The style observers record the input
string, so a cache hit on `currentColor` does not establish that assigning it
again would produce the same native color.

Reproduction with a ready 100 × 100 CanvasSpace:

```js
space.element.style.color = "red";
const form = space.getForm().strokeOnly("currentColor", 10);
space.add(() =>
  form.strokeOnly("currentColor", 10).line([
    [10, 10],
    [90, 10],
  ]),
);
space.play(10);
space.element.style.color = "blue";
space.play(20);
```

The initial stroke is red in both builds. After the CSS change and second draw,
pixel `(20, 10)` is blue, `[0, 0, 255, 255]`, in `b6fc415`, but remains red,
`[255, 0, 0, 255]`, in `9b461c6`. Explicitly assigning
`space.ctx.strokeStyle = "currentColor"` before drawing makes the current build
blue too, confirming that the skipped setter causes the difference.

The setup call outside the animation matters: the frame's saved style cache
contains the literal `currentColor`. Restoring and retaining it lets the next
frame skip a setter whose result depends on CSS outside the observed context.
Absolute colors do not have this dependency.

Recommendation: avoid treating context-dependent color strings as permanently
resolved cache hits. Preserve caching for absolute styles, and add a native
pixel test that changes CSS color between frames. This case is not covered by
the existing direct-write and save/restore tests.

### Remaining Path limitation

The new tree reorders edges only when their left x coordinates are exactly equal.
Giving each otherwise disjoint horizontal bar a small random x offset removes
those ties. The tree then declines the poorly pruning search, and the plain
sweep scans quadratic candidate windows.

The independent scaling probe builds 1-pixel-high bars spaced 3 pixels apart,
each 1,000 pixels wide. It uses a seeded Fisher–Yates shuffle and, for the
staggered case, independent x offsets in `[0, 4)`. Medians at the current head:

| Bars  | Shuffled, equal x | Shuffled, staggered x |
| ----- | ----------------- | --------------------- |
| 1,000 | 2.97 ms           | 12.33 ms              |
| 2,000 | 6.32 ms           | 46.78 ms              |
| 4,000 | 13.60 ms          | 186.55 ms             |

This limitation is acknowledged in the fix-pass account and included in the
repository benchmark. It is not a new regression in these 11 commits. It does
mean the original audit's general x-overlap performance issue should remain
open rather than be marked completely fixed. A different y index could prune
these disjoint bars even when their x coordinates differ.

### A. Stopped-space presses

The finding is right, and wider than unbinding. Players get no actions while
the space is stopped, so any press that ended then (released, cancelled or
abandoned) never ended for them, and the ownership check added in the first fix
pass kept a dragger bound to that contact. Native Chromium touch input (CDP),
pressing and dragging while playing, then stopping, then the variant, then
replaying and dragging with a new contact:

| Variant                           | `b6fc415` | `9b461c6` | Fixed    |
| --------------------------------- | --------- | --------- | -------- |
| Unbound while stopped, tracked    | recovers  | stuck     | recovers |
| Unbound while stopped, forwarded  | stuck     | stuck     | recovers |
| Released while stopped, tracked   | stuck     | stuck     | recovers |
| Released while stopped, forwarded | stuck     | stuck     | recovers |

Stuck is two drags, no drops and `dragging === true`; recovers is four drags
and two drops. The canvas needs `touch-action: none` to reproduce this:
without it Chromium cancels the touch as a pan before the space stops, the
drag ends normally, and every build recovers.

The policy stays: nothing reaches players while stopped. The space remembers
that a press whose start players saw has ended, and sends "out", then "drop"
if it dragged, at the last pointer position, before the first frame when it
plays again. A press that starts and ends while stopped is never sent.
Dropping tracked draggers directly while stopped, as `b6fc415` did, would
leave forwarded UIs stuck and call UI handlers while stopped.

### B. Styles that resolve against CSS

Right. Which strings change when the identical string is assigned again after
a CSS change, in Chromium 151 and Firefox 153 (run through Playwright with
GTK libraries unpacked locally):

| Value                             | Chromium               | Firefox                     |
| --------------------------------- | ---------------------- | --------------------------- |
| `currentColor`                    | re-resolves            | re-resolves                 |
| `Canvas`, `ButtonFace`, `Field`   | re-resolve             | ignore the canvas's scheme  |
| `CanvasText`                      | only after other value | ignores the canvas's scheme |
| `light-dark(red, blue)`           | not parsed             | parsed, ignores the scheme  |
| `2em sans-serif`, `bolder 20px …` | re-resolve             | re-resolve                  |

So a cache hit is not trusted for colors naming `currentColor`,
`light-dark()` or a system color, or for fonts with relative weights or sizes:
the style is written again. Where the test runs matters. Testing strings in
the observers slowed direct `ctx.fillStyle` writes by 5–8%: in Chromium,
reading any character of a short string ("#f03", "teal") there costs about
3.5 ns of a 16 ns write, while seven-character hex and `rgba()` strings cost
nothing. So only cache hits test strings, and the last plain value per style
(fill, stroke, font) is remembered, so a repeated hit costs one more
comparison. A first version of the test made `_set` too large for V8 to
inline twice into `stroke()` (257 to 351 bytes of bytecode); it is now one
call to a tiny helper (301 bytes). Making `_set` smaller still, by sending
rarely repeated styles through the generic path, made join, cap, composite and
font calls 1.15× of 1.0.2, so it was dropped.

The browser test changes CSS between frames for a `currentColor` stroke and a
`Canvas` stroke (whose color scheme changes) and sets a `bolder` font under
two canvas weights. Each part fails without its part of the fix.

### Remaining Path limitation

Left open. A general fix needs a y-ordered search for windows whose edges are
not tied in x. Grouping runs of edges that all overlap in x does not capture
staggered bars, since each bar's left side is a zero-width vertical edge. Fixed
runs ordered by y would capture them but slow the tied case that is now 11×
faster than 1.0.2. It is better done in its own pass with its own benchmarks.

### Sorted convex hulls

The reassessment's table showed presorted hulls at 14.4 ns per point against
11.3 for 1.0.2. The repository benchmark confirms it at 512 points (+26.6%);
unsorted hulls are at parity. Two fixes from the first fix pass cost it:
checking that presorted input is sorted and free of duplicates (about 1.2 ns
per point; x-sorted input with ties or duplicates gave wrong hulls) and the
exact orientation filter (about 1.6 ns). V8 also inlined the filter at four of
its five call sites, against all five for 1.0.2's plain test. The check now
holds the previous point in locals, and the first triangle is tested exactly,
leaving `left` only its loop's four call sites, which V8 inlines. The
repository benchmark now gives 12.8 ns against 10.8 (+18%). Outputs are
identical to `9b461c6` on 10,080 hulls: random, gridded, duplicated,
collinear, nearly collinear, tied in x, huge coordinates and circles, each
unsorted, sorted, and unsorted but passed as sorted. Other attempts were
slower or no faster: skipping the error bound when the products' signs differ
(branches on random data), and one error bound per hull from its extents.
